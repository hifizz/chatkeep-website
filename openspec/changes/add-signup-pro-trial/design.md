## Context

当前系统已有订阅模型（`user_subscription`）与 Pro 权限判定（`trial|active|grace|past_due => isPro=true`），但注册流程不会自动写入试用订阅。
本次变更要把“新用户注册即获得 30 天 Pro 体验”接入到服务端注册链路，并保证幂等、不影响现有付费订阅与 webhook 同步。

## Goals / Non-Goals

**Goals:**
- 在服务端注册成功后自动授予 30 天 Pro 试用，默认计划为 `monthly`、状态为 `trial`。
- 试用授予逻辑具备幂等性，重复触发不重复发放、不覆盖现有有效订阅。
- 试用到期后可自动降级为非 Pro，避免出现“永久 trial”。
- 与现有 Checkout/Webhook/`hasUsedTrial` 逻辑兼容，继续保证“每用户仅一次试用”。

**Non-Goals:**
- 不新增新的支付提供方或新的结算流程。
- 不为历史已注册用户做批量补发。
- 不改动定价页面与营销文案（可在后续变更单独处理）。

## Decisions

- 决策 1：在服务端注册后置钩子中发放试用（而非前端 `signUp` 成功后调用）。
  - 理由：服务端路径不可被前端绕过，且能保证所有注册入口行为一致。
  - 备选方案：前端注册成功后调用 RPC 发放试用。
  - 放弃原因：前端可被跳过/重试，安全性和一致性差。

- 决策 2：新增 billing 域服务函数（如 `grantSignupTrialIfEligible`）封装发放逻辑，内部先检查现有订阅，再执行创建。
  - 理由：避免在 `auth.ts` 直接操作数据库，保持职责清晰，便于单测。
  - 备选方案：在 `auth.ts` 中直接调用 `upsertSubscription`。
  - 放弃原因：`upsert` 在已有记录时会覆盖状态，存在把已付费状态改回 trial 的风险。

- 决策 3：试用时长固定 30 天，基于“注册时间 + 30 天”写入 `currentPeriodEnd` 与 `trialEndsAt`。
  - 理由：满足需求且实现简单，避免引入额外配置项。
  - 备选方案：新增环境变量 `SIGNUP_TRIAL_DAYS`。
  - 放弃原因：当前需求明确为 1 个月，提前参数化属于过度设计。

- 决策 4：在订阅读取链路增加 trial 到期判定并自动降级（与现有 `past_due` 读时降级策略保持一致）。
  - 理由：当前注册送 trial 不依赖支付提供方 webhook，需要本地兜底过期机制。
  - 备选方案：新增定时任务每日扫描过期 trial。
  - 放弃原因：当前项目未内置任务调度，读时判定更小改动且可立即生效。

## Risks / Trade-offs

- 注册后置钩子执行失败会导致“账号创建成功但未拿到 trial” → 记录错误日志并保持注册成功，后续可通过一次性补偿脚本修复。
- 读时降级仅在用户访问时触发，数据库中的过期状态可能短暂滞后 → 接受该权衡，后续如引入定时任务可再改为主动清理。
- 如 future 需求需要多种赠送来源（活动码/邀请），“trial 来源”字段可能不足 → 当前先保持最小实现，避免本次扩展数据模型。

## Migration Plan

1. 在 billing 模块新增“注册送 trial”服务函数与对应单测。
2. 在 `auth` 服务端注册后置钩子中调用该函数。
3. 在订阅读取逻辑加入 `trialEndsAt` 超时降级判断。
4. 本地验证：新用户注册后 `/profile` 显示 Pro Trial；模拟超时后降级为 Free。
5. 回滚策略：移除后置钩子调用，并清理异常插入的 trial 记录（按 `status=trial` 且无 provider 订阅号筛选）。

## Open Questions

- 注册后置钩子失败是否需要加入告警（例如 Sentry）而不是仅日志？
